@@summary

คณะทำงานได้ทดสอบสมรรถนะของภาษาโปรแกรม Arc เทียบกับ Rust, Go, Java และ Python ด้วยโจทย์เดียวกัน ๑๐ โจทย์ ทุกภาษาให้ผลลัพธ์ตรงกันทุกตัวอักษรก่อนการวัด และวัดโจทย์ละ ๑๐ รอบโดยสุ่มลำดับใหม่ทุกรอบ สรุปผลสำคัญได้ดังนี้

  1. ด้านเวลาประมวลผลโดยรวม Arc ได้ค่าเฉลี่ยเรขาคณิตต่ำที่สุดที่ ๑.๒๔ เท่าของภาษาที่เร็วที่สุดในแต่ละโจทย์ ตามด้วย Rust ๑.๓๐ เท่า Go ๑.๔๕ เท่า Java ๑.๖๑ เท่า และ Python ๒๗.๕ เท่า แต่อันดับหนึ่งนี้ไม่มั่นคง เพราะได้มาจากโจทย์การเรียงลำดับเป็นหลัก ซึ่งไลบรารีมาตรฐานของ Arc ใช้อัลกอริทึม radix sort ขณะที่ภาษาอื่นใช้การเรียงลำดับแบบเปรียบเทียบ เมื่อตัดโจทย์นี้ออก อันดับจะเปลี่ยนเป็น Go ๑.๒๕ เท่า Arc ๑.๒๗ เท่า และ Rust ๑.๒๙ เท่า ซึ่งต่างกันไม่เกินร้อยละ ๓ (ตารางที่ ๗)
  2. ข้อสรุปที่ข้อมูลรองรับ คือ Arc อยู่ในกลุ่มสมรรถนะเดียวกับ Rust และ Go ในงานคำนวณ ไม่ใช่เร็วกว่าภาษาทั้งสองโดยรวม Arc เร็วที่สุด ๖ จาก ๑๐ โจทย์ แต่ใน ๓ โจทย์ (fib, mandelbrot และ nbody) นำภาษาอันดับสองเพียงร้อยละ ๒–๗
  3. จุดอ่อนที่ชัดเจนของ Arc ได้แก่ งานที่จองหน่วยความจำจำนวนมาก (binary_trees ช้ากว่า Java ๓.๘๐ เท่า) งานประมวลผลข้อความ (text ช้ากว่า Go ๑.๖๘ เท่า และ Rust ๑.๕๐ เท่า) และการใช้หน่วยความจำในงานเหล่านั้น ซึ่งสูงกว่า Rust ๔.๖–๕.๒ เท่า
  4. จุดแข็งด้านการใช้งาน โปรแกรม Arc เริ่มทำงานใน ๓.๔ มิลลิวินาที (ใกล้เคียง Rust ๓.๐ และ Go ๔.๑ มิลลิวินาที) ไฟล์ปฏิบัติการมีขนาดประมาณ ๕๑ KB เล็กกว่า Rust ประมาณ ๙ เท่า และเล็กกว่า Go ประมาณ ๔๘ เท่า และผลวัดของ Arc คงที่ที่สุด (CV ไม่เกินร้อยละ ๔.๐ ทุกโจทย์)
  5. Python (CPython) ช้ากว่าภาษาที่เร็วที่สุดเฉลี่ย ๒๗.๕ เท่า ยกเว้นงานสตริงและตารางแฮชที่ช้ากว่าเพียง ๓.๕–๔.๖ เท่า เพราะงานส่วนใหญ่ทำในไลบรารีที่เขียนด้วยภาษา C

โดยสรุป ภาษา Arc มีสมรรถนะระดับเดียวกับภาษาคอมไพล์ชั้นนำในงานคำนวณ แต่ยังด้อยกว่าในงานที่พึ่งพาตัวเก็บขยะและงานสตริง ยังไม่ควรกล่าวอ้างว่า Arc เร็วกว่า Rust หรือ Go โดยรวม รายละเอียดอยู่ในส่วนที่ ๕ และ ๖

@@background

ภาษาโปรแกรม Arc ได้รับการพัฒนาคอมไพเลอร์ใหม่ทั้งหมดให้เป็นภาษาแบบกำหนดชนิดข้อมูลตายตัว (statically typed) ที่คอมไพล์เป็นรหัสเครื่องผ่านภาษา C และมีตัวเก็บขยะ (garbage collector) ในตัว เพื่อให้ใช้งานได้จริงในระดับเดียวกับภาษาที่ใช้กันในอุตสาหกรรม การประเมินว่าภาษาอยู่ในระดับใดจำเป็นต้องอาศัยการวัดที่เป็นกลาง ตรวจสอบได้ และทำซ้ำได้ ไม่ใช่การเลือกเฉพาะโจทย์ที่ได้เปรียบ

รายงานฉบับนี้จึงทดสอบภาษา Arc เทียบกับ Rust และ Go ซึ่งเป็นภาษาคอมไพล์สมรรถนะสูง Java ซึ่งเป็นภาษาบนเครื่องเสมือนที่มีตัวแปลภาษาขณะทำงาน (JIT) และ Python ซึ่งเป็นภาษาแบบอินเทอร์พรีเตอร์ที่ได้รับความนิยมสูงสุด โดยใช้โจทย์และเงื่อนไขเดียวกันทุกประการ

การเปิดเผยส่วนได้ส่วนเสีย ผู้จัดทำรายงานเป็นผู้พัฒนาภาษา Arc เอง เพื่อป้องกันอคติ ซอร์สโค้ดของทุกโจทย์ในทุกภาษา ตัวควบคุมการทดสอบ และข้อมูลดิบทุกครั้งที่วัด เปิดเผยไว้ในโฟลเดอร์ benchmarks/suite/ ของโครงการ ผู้ใดก็สามารถตรวจสอบและทำซ้ำได้ตามภาคผนวก ค

@@method

๔.๑ หลักเกณฑ์ความเป็นกลาง การทดสอบยึดหลักเกณฑ์ต่อไปนี้อย่างเคร่งครัด

  1. อัลกอริทึมเดียวกัน ทุกภาษาทำงานตามขั้นตอนเดียวกันทุกขั้น ใช้โครงสร้างข้อมูลระดับเดียวกัน และเขียนลูปเองทั้งหมด ข้อยกเว้นที่ต้องเปิดเผย คือฟังก์ชันเรียงลำดับของไลบรารีมาตรฐาน ซึ่งแต่ละภาษาใช้อัลกอริทึมต่างกัน ได้แก่ Arc ใช้ LSD radix sort, Rust ใช้ sort_unstable (quicksort แบบ pattern-defeating), Go ใช้ slices.Sort (pdqsort), Java ใช้ Arrays.sort (dual-pivot quicksort) และ Python ใช้ list.sort (Timsort) ผลของความต่างนี้วิเคราะห์ไว้ในข้อ ๕.๖ และ ๖.๒
  2. ใช้เฉพาะไลบรารีมาตรฐาน สำหรับการเรียงลำดับ ตารางแฮช และการจัดการสตริง ห้ามใช้ไลบรารีภายนอก (เช่น NumPy) และห้ามใช้เทคนิคเฉพาะภาษาที่ลดปริมาณงานจริง
  3. โค้ดของผู้ทดสอบทำงานเธรดเดียว ทุกภาษา ไม่มีการประมวลผลแบบขนาน อย่างไรก็ตาม รันไทม์ของ Go และ Java ใช้เธรดเบื้องหลังสำหรับตัวเก็บขยะและตัวแปลภาษาขณะทำงานตามค่าเริ่มต้น ซึ่งไม่ได้ปิด เพราะเป็นสภาพการใช้งานจริง ผลกระทบของเรื่องนี้แสดงด้วยการวัดเวลา CPU (ข้อ ๖.๕)
  4. อินพุตเดียวกัน ส่งผ่านอาร์กิวเมนต์บรรทัดคำสั่ง เพื่อไม่ให้คอมไพเลอร์คำนวณผลลัพธ์ล่วงหน้าได้
  5. ผลลัพธ์ต้องตรงกันทุกตัวอักษร ระหว่างทั้ง ๕ ภาษา ก่อนเริ่มการวัด (ภาคผนวก ข) โจทย์ที่ผลลัพธ์ไม่ตรงกันจะไม่ถูกวัด
  6. ตั้งค่าการคอมไพล์แบบ release ตามมาตรฐานของแต่ละภาษา ไม่ใช้ตัวเลือกเฉพาะซีพียู (เช่น -march=native) กับภาษาใด ยกเว้น JIT ของ Java ซึ่งปรับตามซีพียูโดยธรรมชาติของมัน
  7. การปรับโค้ดเพียงจุดเดียว คือโจทย์ mandelbrot ในภาษา Go ใช้ float64(...) ครอบผลคูณ เพื่อไม่ให้ Go รวมการคูณและบวกเป็นคำสั่ง fused multiply-add ซึ่งให้ผลทศนิยมต่างจากภาษาอื่น การปรับนี้ทำให้ทุกภาษาคำนวณตามมาตรฐาน IEEE-754 เหมือนกัน

๔.๒ สิ่งที่วัด วัดเวลาจริง (wall-clock) ตั้งแต่เริ่มสร้างโปรเซสจนโปรแกรมจบ ซึ่งรวมเวลาเริ่มต้นของ JVM และอินเทอร์พรีเตอร์ เพราะเป็นต้นทุนจริงของโปรแกรมแบบบรรทัดคำสั่ง และวัดเวลา CPU (user + system) กับหน่วยความจำสูงสุด (peak RSS) ของแต่ละโปรเซสด้วยการเรียกระบบ wait4 นอกจากนี้ยังวัดเวลาเริ่มต้นโปรแกรม เวลาคอมไพล์ ขนาดไฟล์ที่ได้ และจำนวนบรรทัดโค้ด

๔.๓ ขั้นตอนการวัด

  1. คอมไพล์ทุกโปรแกรมใหม่ ๓ ครั้งโดยไม่ใช้แคชของโปรแกรมนั้น แล้วใช้มัธยฐานเป็นเวลาคอมไพล์
  2. รันรอบอุ่นเครื่อง ๑ รอบโดยไม่นับผล เพื่อตัดผลของการโหลดไฟล์ครั้งแรกและการตรวจสอบไฟล์ปฏิบัติการใหม่ของ macOS ซึ่งวัดได้ ๐.๓๓–๐.๓๙ วินาทีในการรันครั้งแรกของไฟล์ที่เพิ่งคอมไพล์
  3. วัดจริง ๑๐ รอบ แต่ละรอบรันครบทั้ง ๕๐ คู่ (๑๐ โจทย์ × ๕ ภาษา) โดยสุ่มลำดับใหม่ทุกรอบ (random seed 20261118) เพื่อให้ผลของความร้อนสะสม การลดความเร็วของซีพียู และงานเบื้องหลังของระบบ กระจายไปยังทุกภาษาอย่างเท่ากัน
  4. วัดเวลาเริ่มต้นโปรแกรมแยกต่างหาก ภาษาละ ๒๐ ครั้ง สลับลำดับแบบสุ่ม

๔.๔ การวิเคราะห์ทางสถิติ ใช้มัธยฐานของเวลาจริงในการจัดอันดับ เพราะทนต่อค่าผิดปกติจากงานเบื้องหลังของระบบ และรายงานค่าเฉลี่ย ค่าต่ำสุด ค่าสูงสุด ส่วนเบี่ยงเบนมาตรฐาน สัมประสิทธิ์การแปรผัน (CV) และช่วงเชื่อมั่น ๙๕% (การแจกแจงแบบ t, n = ๑๐) ไว้ในภาคผนวก ก ผลรวมของแต่ละภาษาใช้ค่าเฉลี่ยเรขาคณิตของอัตราส่วนเวลาเทียบกับภาษาที่เร็วที่สุดในแต่ละโจทย์ ซึ่งเป็นวิธีมาตรฐานของการรวมผลเบนช์มาร์ก ไม่ใช้ค่าเฉลี่ยเลขคณิตของเวลา เพราะโจทย์ที่ใช้เวลานานจะครอบงำผลรวม และตรวจความมั่นคงของอันดับด้วยการคำนวณซ้ำภายใต้เกณฑ์อื่น (ข้อ ๕.๖)

๔.๕ การจัดเก็บไฟล์ ไฟล์ที่คอมไพล์ได้ แคชของคอมไพเลอร์ และไฟล์ชั่วคราวทั้งหมด จัดเก็บบนหน่วยความจำ SSD ภายนอก ตามข้อกำหนดของโครงการ

@@results_time

จากตารางที่ ๒ แบ่งผลได้เป็น ๓ กลุ่มตามลักษณะงาน ดังนี้

กลุ่มที่ ๑ งานคำนวณ (fib, sieve, nbody, matmul, mandelbrot และ fannkuch) Arc, Rust และ Go ใช้เวลาใกล้เคียงกัน Arc เร็วที่สุด ๕ จาก ๖ โจทย์ แต่ส่วนต่างเทียบกับภาษาอันดับสองมีขนาดต่างกันมาก ได้แก่ mandelbrot ร้อยละ ๒ fib ร้อยละ ๓ nbody ร้อยละ ๗ matmul ร้อยละ ๑๕ และ sieve ร้อยละ ๑๖ ส่วนโจทย์ fannkuch นั้น Rust เร็วที่สุด และ Arc ช้ากว่า ๑.๑๒ เท่า Java ช้ากว่าภาษาที่เร็วที่สุด ๑.๑๕–๒.๙๐ เท่า โดยช้าที่สุดในโจทย์ matmul ซึ่งภาษาคอมไพล์ใช้เวลาเพียง ๓๓–๓๙ มิลลิวินาที โปรแกรม Java จึงจบก่อนที่ JIT จะคอมไพล์โค้ดได้เต็มที่ Python ช้ากว่า ๓๐–๑๐๐ เท่าในกลุ่มนี้

กลุ่มที่ ๒ งานจองหน่วยความจำ (binary_trees) Java เร็วที่สุดอย่างชัดเจนที่ ๐.๓๔ วินาที ตามด้วย Go ๓.๒๓ เท่า Arc ๓.๘๐ เท่า และ Rust ๔.๒๐ เท่า ภาษาที่มีตัวเก็บขยะแบบแยกรุ่น (generational) และจองหน่วยความจำด้วยการเลื่อนตัวชี้ (bump allocation) อย่าง Java ได้เปรียบมากในงานประเภทนี้ ส่วน Rust จองและคืนหน่วยความจำทีละโหนดผ่านตัวจัดสรรของระบบ

กลุ่มที่ ๓ งานสตริง ตารางแฮช และการเรียงลำดับ โจทย์ wordcount ผลของ Java (๐.๑๘๐๒ วินาที) และ Go (๐.๑๘๐๓ วินาที) ต่างกันน้อยกว่าช่วงเชื่อมั่น จึงถือว่าเสมอกัน Arc ช้ากว่า ๑.๑๕ เท่า และ Rust ช้ากว่า ๑.๓๙ เท่า โจทย์ sort Arc เร็วที่สุดที่ ๐.๐๗๐ วินาที ตามด้วย Rust ๑.๓๙ เท่า Go ๕.๗๗ เท่า และ Java ๖.๐๖ เท่า ส่วนต่างที่มากนี้มาจากความต่างของอัลกอริทึมในไลบรารีมาตรฐาน (ข้อ ๖.๒) ไม่ได้มาจากคุณภาพของคอมไพเลอร์ โจทย์ text Go เร็วที่สุด ตามด้วย Rust ๑.๑๒ เท่า ส่วน Arc ช้ากว่า ๑.๖๘ เท่า เกือบเท่ากับ Java (๑.๗๓ เท่า) ซึ่งเป็นผลที่แย่ที่สุดของ Arc เมื่อเทียบกับภาษาคอมไพล์ด้วยกัน

หน่วยความจำพื้นฐาน ในโจทย์ที่แทบไม่จองหน่วยความจำ (fib, nbody, mandelbrot และ fannkuch) Arc และ Rust ใช้ประมาณ ๑.๗–๑.๘ MB Go ใช้ประมาณ ๔.๒ MB Python ใช้ประมาณ ๑๓–๑๔ MB และ Java ใช้ ๓๘–๔๒ MB ซึ่งเป็นขนาดของ JVM เอง

Arc ใช้หน่วยความจำมากกว่า Rust อย่างมีนัยสำคัญในงานที่จองหน่วยความจำ ได้แก่ binary_trees ๙๓.๐ MB เทียบกับ Rust ๑๗.๙ MB (๕.๒ เท่า) และ Go ๓๙.๔ MB, text ๔๒๓.๖ MB เทียบกับ Rust ๙๒.๙ MB (๔.๖ เท่า) และ Go ๑๐๖.๗ MB, sort ๗๘.๑ MB เทียบกับ Rust ๔๐.๐ MB (radix sort ต้องใช้บัฟเฟอร์ชั่วคราวขนาดเท่ากับอาร์เรย์ คือ ๕ ล้านค่า × ๘ ไบต์ = ๔๐ MB) และ wordcount ๑๕.๗ MB เทียบกับ Rust ๖.๙ MB สาเหตุหลักคือตัวเก็บขยะของ Arc เริ่มทำงานเมื่อมีการจองหน่วยความจำใหม่เท่ากับขนาดข้อมูลที่ยังใช้งานอยู่ (ขั้นต่ำ ๘ MB) จึงยอมให้หน่วยความจำโตได้ประมาณ ๒ เท่าของข้อมูลที่ใช้งานจริง

Java แลกหน่วยความจำกับความเร็ว ในโจทย์ binary_trees ที่ Java เร็วที่สุด Java ใช้หน่วยความจำ ๕๙๕.๖ MB มากกว่า Rust ๓๓ เท่า และ Python ใช้หน่วยความจำ ๓๙๔.๙ MB ในโจทย์ sieve เพราะรายการ (list) ของ Python เก็บตัวชี้ขนาด ๘ ไบต์ต่อหนึ่งค่า ขณะที่ภาษาอื่นใช้ ๑ ไบต์ เมื่อรวมทุกโจทย์ด้วยค่าเฉลี่ยเรขาคณิต (ตารางที่ ๗) Rust ใช้หน่วยความจำน้อยที่สุด ตามด้วย Arc ๑.๕๙ เท่า Go ๑.๗๐ เท่า Python ๕.๑๑ เท่า และ Java ๑๐.๙ เท่า

@@results_build

เวลาเริ่มต้นโปรแกรม (ตารางที่ ๔) Rust เร็วที่สุดที่ ๓.๐ มิลลิวินาที Arc ๓.๔ มิลลิวินาที และ Go ๔.๑ มิลลิวินาที ซึ่งต่างกันน้อยมากในการใช้งานจริง ส่วน Python ใช้ ๒๐.๖ มิลลิวินาที และ Java ใช้ ๒๙.๕ มิลลิวินาที ต้นทุนนี้รวมอยู่ในเวลาของทุกโจทย์ จึงมีผลมากที่สุดกับโจทย์ที่ใช้เวลาสั้น เช่น matmul

เวลาคอมไพล์ ทุกภาษาใช้เวลาใกล้เคียงกันที่ ๐.๒๒–๐.๒๘ วินาทีต่อโปรแกรม เวลาของ Arc รวมเวลาที่คอมไพเลอร์ภาษา C ใช้ด้วย โปรแกรมทดสอบเป็นไฟล์เดียวขนาดเล็ก ผลนี้จึงไม่สะท้อนเวลาคอมไพล์ของโครงการขนาดใหญ่ ซึ่งแต่ละภาษามีพฤติกรรมต่างกันมาก

ขนาดไฟล์ ไฟล์ปฏิบัติการของ Arc มีขนาดประมาณ ๕๑ KB Rust ประมาณ ๔๗๕ KB และ Go ประมาณ ๒.๔ MB เพราะ Go รวมรันไทม์และตัวเก็บขยะไว้ในไฟล์แบบคงที่ จำนวนบรรทัดโค้ด รวมทั้ง ๑๐ โจทย์ Python น้อยที่สุด (๒๙๐ บรรทัด) ตามด้วย Java ๓๑๘ Rust ๓๒๐ Arc ๓๓๔ และ Go ๔๓๕ บรรทัด แสดงว่า Arc ไม่ได้กระชับกว่า Rust หรือ Java อย่างมีนัยสำคัญ

@@discussion

๖.๑ เหตุที่ Arc เร็วในงานคำนวณ Arc คอมไพล์เป็นภาษา C แล้วใช้คอมไพเลอร์ clang ระดับ -O3 ซึ่งใช้ตัวปรับแต่งโค้ด LLVM ชุดเดียวกับที่ Rust ใช้ ความเร็วในกลุ่มที่ ๑ จึงสะท้อนคุณภาพของ LLVM เป็นหลัก สิ่งที่ Arc ทำได้คือไม่เพิ่มต้นทุนแฝง เช่น เก็บจำนวนเต็มและทศนิยมในอาร์เรย์โดยตรงโดยไม่ห่อเป็นออบเจกต์ ส่วนต่างร้อยละ ๒–๗ ใน fib, mandelbrot และ nbody จึงไม่ควรตีความว่า Arc ดีกว่า Rust ในเชิงหลักการ คณะทำงานไม่ได้วิเคราะห์สาเหตุของส่วนต่างในระดับคำสั่งเครื่อง

๖.๒ ผลของโจทย์การเรียงลำดับ Arc ใช้ radix sort กับอาร์เรย์จำนวนเต็มและทศนิยม ซึ่งมีความซับซ้อนเชิงเวลาแบบเชิงเส้น ขณะที่ภาษาอื่นใช้การเรียงลำดับแบบเปรียบเทียบซึ่งมีความซับซ้อน O(n log n) นี่เป็นข้อได้เปรียบจริงของไลบรารีมาตรฐานของ Arc แต่ได้มาด้วยหน่วยความจำเพิ่มเท่าตัว และใช้ได้เฉพาะข้อมูลตัวเลข การเรียงสตริงยังใช้ qsort ของภาษา C ภาษาอื่นสามารถใช้ radix sort ได้ผ่านไลบรารีภายนอก ซึ่งหลักเกณฑ์ข้อ ๔.๑ ไม่อนุญาต รายงานนี้จึงแสดงทั้งอันดับที่รวมและไม่รวมโจทย์นี้ และถือว่าอันดับที่ไม่รวม sort สะท้อนความสามารถของคอมไพเลอร์ได้ดีกว่า

๖.๓ ตัวเก็บขยะ ตัวเก็บขยะของ Arc เป็นแบบ mark-and-sweep ที่ไม่แยกรุ่น และหยุดโปรแกรมทั้งหมดระหว่างทำงาน แม้จะเร็วกว่า Rust ที่คืนหน่วยความจำทีละโหนด แต่ช้ากว่า Java ๓.๘๐ เท่า และใช้หน่วยความจำมากกว่า Rust ๕.๒ เท่าในโจทย์ binary_trees นี่คือจุดที่ต้องปรับปรุงเป็นลำดับแรก หากต้องการใช้ Arc กับงานที่สร้างออบเจกต์จำนวนมาก เช่น เว็บเซิร์ฟเวอร์หรือคอมไพเลอร์

๖.๔ งานสตริง ฟังก์ชัน split ของ Arc คัดลอกสตริงย่อยทุกชิ้นเป็นออบเจกต์ใหม่ และระงับตัวเก็บขยะระหว่างการแยก ขณะที่ Rust คืนค่าเป็นการอ้างอิงไปยังสตริงเดิม (&str) และ Go ใช้สตริงย่อยที่ชี้ไปยังหน่วยความจำเดิม โจทย์ text ซึ่งแยกข้อความ ๑ ล้านบรรทัดจึงทำให้ Arc ช้ากว่า Go ๑.๖๘ เท่า และใช้หน่วยความจำ ๔๒๓.๖ MB ภาษา Arc ยังไม่มีชนิดข้อมูลสำหรับมุมมองของสตริง (string view) ซึ่งเป็นช่องว่างด้านการออกแบบที่ควรแก้ไข

๖.๕ เวลา CPU และเธรดเบื้องหลัง รันไทม์ของ Go และ Java ใช้แกนประมวลผลเพิ่มเติมโดยอัตโนมัติ ในโจทย์ binary_trees Go ใช้เวลา CPU ๒.๔๖ วินาที แต่เวลาจริงเพียง ๑.๑๐ วินาที เพราะตัวเก็บขยะทำงานขนานบนแกนอื่น และในโจทย์ text Java ใช้เวลา CPU ๐.๘๐ วินาที ขณะที่เวลาจริง ๐.๓๘ วินาที ส่วน Arc และ Rust ใช้แกนเดียว เมื่อคิดจากเวลา CPU (ตารางที่ ๗) Arc ได้ ๑.๑๙ เท่า Rust ๑.๒๕ เท่า Go ๑.๕๓ เท่า และ Java ๑.๘๙ เท่า เกณฑ์นี้สำคัญเมื่อเครื่องรันหลายโปรแกรมพร้อมกัน เช่น บนเซิร์ฟเวอร์

๖.๖ ความน่าเชื่อถือของผลวัด ค่า CV ของ Arc ไม่เกินร้อยละ ๔.๐ ในทุกโจทย์ ค่า CV ที่สูงที่สุดของการทดสอบนี้ได้แก่ Java ในโจทย์ sieve (ร้อยละ ๑๙.๙) และ wordcount (ร้อยละ ๑๗.๗) และ Go ในโจทย์ matmul (ร้อยละ ๑๕.๑) ซึ่งเกิดจากจังหวะการทำงานของ JIT และตัวเก็บขยะที่ต่างกันในแต่ละครั้ง การใช้มัธยฐานทำให้อันดับไม่ถูกบิดเบือนจากค่าผิดปกติเหล่านี้ ส่วนต่างที่น้อยกว่าช่วงเชื่อมั่น ๙๕% ในภาคผนวก ก ควรถือว่าเสมอกัน

๖.๗ คำตอบต่อคำถามว่า Arc อยู่ในระดับเดียวกับ Rust และ Go หรือไม่ ในด้านสมรรถนะของงานคำนวณ คำตอบคือใช่ ในด้านงานที่พึ่งพาตัวเก็บขยะ งานสตริง และการใช้หน่วยความจำ คำตอบคือยังไม่ใช่ นอกจากนี้ การทดสอบนี้ไม่ได้วัดการประมวลผลแบบขนาน ระบบนิเวศของไลบรารี และเครื่องมือพัฒนา ซึ่ง Rust, Go และ Java เหนือกว่า Arc อย่างมาก

@@limitations
  1. ทดสอบบนเครื่องเดียว คือ MacBook Air (Apple M2, ไม่มีพัดลมระบายความร้อน) ใช้พลังงานจากแบตเตอรี่โดยปิดโหมดประหยัดพลังงาน ผลอาจแตกต่างบนซีพียูหรือระบบปฏิบัติการอื่น ความร้อนสะสมอาจลดความเร็วของซีพียู แต่การสุ่มลำดับทุกรอบทำให้ผลกระทบนี้เกิดกับทุกภาษาเท่ากัน
  2. วัดแบบต้นจนจบ (end-to-end) ซึ่งรวมเวลาเริ่มต้นโปรแกรม ทำให้ภาษาที่คอมไพล์เป็นรหัสเครื่องได้เปรียบในโจทย์ที่ใช้เวลาสั้น การทดสอบนี้ไม่ได้วัดสมรรถนะของ Java หลัง JIT ทำงานเต็มที่ในโปรแกรมที่รันต่อเนื่องนาน (steady state)
  3. โจทย์ส่วนใหญ่ใช้เวลาน้อยกว่า ๐.๕ วินาที สำหรับภาษาคอมไพล์ ส่วนต่างที่เป็นร้อยละไม่กี่หน่วยจึงไวต่อเวลาเริ่มต้นโปรแกรมและสัญญาณรบกวนของระบบ
  4. ไลบรารีมาตรฐานใช้อัลกอริทึมต่างกัน ในการเรียงลำดับ (ข้อ ๔.๑) ซึ่งทำให้ Arc ได้เปรียบในโจทย์ sort ผลรวมที่ไม่รวมโจทย์นี้แสดงไว้ในตารางที่ ๗
  5. Python วัดด้วย CPython ๓.๑๓ ซึ่งเป็นตัวแปลภาษามาตรฐาน ไม่ได้ใช้ PyPy หรือไลบรารีประมวลผลแบบเวกเตอร์ (เช่น NumPy) งานจริงที่ใช้ไลบรารีเหล่านั้นจะเร็วกว่าที่วัดได้ในรายงานนี้มาก
  6. โค้ดทดสอบทำงานเธรดเดียวเท่านั้น จึงไม่สะท้อนความสามารถด้านการประมวลผลแบบขนาน ซึ่ง Go, Java และ Rust ทำได้ดี แต่ภาษา Arc ยังไม่รองรับ
  7. Java ใช้ค่าเริ่มต้นของหน่วยความจำ heap (สูงสุดหนึ่งในสี่ของหน่วยความจำเครื่อง) ซึ่งแลกการใช้หน่วยความจำที่มากขึ้นกับความเร็วที่สูงขึ้น การจำกัด heap จะเปลี่ยนผลทั้งสองด้าน
  8. เป็นโจทย์ทดสอบขนาดเล็ก (microbenchmark) ที่วัดความสามารถเฉพาะด้าน ไม่ใช่แอปพลิเคชันจริงทั้งระบบ ซึ่งมีปัจจัยอื่น เช่น I/O ไลบรารี และระบบนิเวศของภาษา
  9. ผู้จัดทำเป็นผู้พัฒนาภาษา Arc แม้จะใช้หลักเกณฑ์ในข้อ ๔.๑ อย่างเคร่งครัด ผู้อ่านควรตรวจสอบซอร์สโค้ดและทำซ้ำการทดสอบด้วยตนเอง
@@conclusion

๘.๑ สรุปผล จากการวัด ๕๐๐ ครั้งใน ๑๐ โจทย์ ภาษา Arc มีสมรรถนะด้านเวลาอยู่ในกลุ่มเดียวกับ Rust และ Go โดยได้อันดับหนึ่งตามเกณฑ์หลัก (๑.๒๔ เท่า) และอันดับสองเมื่อไม่รวมโจทย์การเรียงลำดับ (๑.๒๗ เท่า รองจาก Go ๑.๒๕ เท่า) เร็วกว่า Java โดยรวม และเร็วกว่า CPython ประมาณ ๒๒ เท่าเมื่อคิดด้วยค่าเฉลี่ยเรขาคณิต Arc มีเวลาเริ่มต้นและขนาดไฟล์ในระดับเดียวกับหรือดีกว่าภาษาคอมไพล์อื่น แต่ยังด้อยกว่าอย่างชัดเจนในงานที่จองหน่วยความจำจำนวนมาก งานสตริง และการใช้หน่วยความจำ

๘.๒ ข้อเสนอแนะ เรียงตามลำดับความสำคัญ

  1. พัฒนาตัวเก็บขยะให้แยกรุ่นและจองหน่วยความจำแบบเลื่อนตัวชี้ และปรับเกณฑ์การเริ่มทำงานให้หน่วยความจำไม่โตเกินจำเป็น เพื่อลดช่องว่างกับ Java ในโจทย์ binary_trees และลดหน่วยความจำให้ใกล้เคียง Go
  2. เพิ่มชนิดข้อมูลมุมมองของสตริง ให้ split และการตัดสตริงไม่ต้องคัดลอกข้อมูล และไม่ต้องระงับตัวเก็บขยะเป็นเวลานาน
  3. เพิ่มการประมวลผลแบบขนาน เช่น เธรดหรือ task เพราะเป็นความสามารถพื้นฐานที่ Rust, Go และ Java มี และการทดสอบนี้ยังไม่ได้วัด
  4. ทดสอบซ้ำบน Linux x86-64 และเครื่องที่มีพัดลมระบายความร้อน เพิ่มการวัด Java แบบ steady state และ PyPy และเพิ่มโจทย์ขนาดใหญ่ที่ใกล้เคียงแอปพลิเคชันจริง
  5. บรรจุชุดทดสอบนี้ไว้ในระบบ CI เพื่อตรวจจับสมรรถนะที่ถดถอยในการพัฒนาครั้งต่อไป
